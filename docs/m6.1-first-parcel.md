# M6.1 — The first element instance, and the field it lives in

M5 ended with `Spell` carrying everything the simulation needs: what drives it
(`driver`), how hard (`strength()`), which way it leans (`balance`), how much of
that is spin (`spin`), and what substance it demands (`demand`).

Nothing reads any of it. M6 is where a compiled spell finally *does* something.

This first task does **not** make anything move. It builds the two nouns
everything after it needs: a **parcel** (one lump of stuff) and a **field** (the
space it sits in). Motion is M6.3, and trying to do both at once is how you end
up with a physics bug you cannot tell apart from a bookkeeping bug.

## 0. Every symbol, spelled out

Nothing later reintroduces these.

### The vector

| Symbol | Meaning |
| --- | --- |
| `Vec2` | A pair of `f32` used as *either* a position or a direction-and-length |
| `x`, `y` | Its two components. In pixels for a position; pixels-per-second for a velocity |
| `‖v‖` | "the length of v" — `sqrt(x² + y²)`. Pythagoras, nothing more |
| `v̂` | "v hat" — `v` divided by its own length. Length exactly 1, direction unchanged |
| `a · b` | The **dot product**, `a.x*b.x + a.y*b.y`. One number, not a vector |

### The parcel

| Symbol | Meaning |
| --- | --- |
| `substance` | *What* it is made of — `"air"`, `"water"`, `"stone"`. A name from the catalogue |
| `at` | Where it is, in the same pixel coordinates the pad draws in |
| `velocity` | How fast and which way, in pixels per second |
| `mass` | How much of it there is. The quantity conservation is about (§3.2) |
| `temperature` | How hot, in whatever unit you pick — pick one and write it down |

### The field

| Symbol | Meaning |
| --- | --- |
| `cell` | One square of the grid. The field is `width × height` of them |
| `cell_size` | How many pixels wide one cell is |
| `origin` | The world position of the **corner** of cell `(0, 0)` |
| `(col, row)` | Which cell, counted from `origin`. `col` runs across, `row` runs down |
| `index` | That cell's slot in a flat `Vec`. Row-major: `row * width + col` |
| `density` | Mass per cell. Derived from the parcels in it, never stored on a parcel |
| `flow` | The average velocity of the parcels in a cell |

**Row-major** means the flat list goes across the first row, then across the
second, and so on. `(2, 1)` in a 5-wide grid is slot `1*5 + 2 = 7`.

## Part A — the vector (steps 1–11)

### Why write one at all

`glam` would satisfy §4.1 perfectly — it is pure Rust and compiles to wasm. Two
honest reasons not to reach for it: sixty lines is a small price against a new
dependency in a crate that has exactly two, and operator overloading is a piece
of Rust you have not written yet. If you would rather have the dependency, take
it — but say so in the module doc, because §8 wants the *why*.

`Point` is not the answer. It carries `stroke_id`, which is a fact about ink, and
a parcel of steam has no stroke.

**1.** Make `crates/magic-core/src/sim/vec2.rs`.

**2.** Declare it:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Default)]
pub struct Vec2 {
    pub x: f32,
    pub y: f32,
}
```

`Copy` because two `f32` are cheaper to copy than to reference. `PartialEq` and
not `Eq` because `f32` has `NaN`, which is not equal to itself.

**3.** Add `pub const ZERO: Vec2` and `pub fn new(x: f32, y: f32) -> Vec2`.

**4.** Add `pub fn length_squared(self) -> f32`. It is `x*x + y*y`.

**5.** Add `pub fn length(self) -> f32` — the square root of step 4.

Keep both. Comparing two lengths never needs the root, and M4.7 got the
recognizer from 0.87ms to 0.41ms on exactly that observation.

**6.** Add `pub fn dot(self, other: Vec2) -> f32`.

**7.** Add `pub fn normalize_or_zero(self) -> Vec2`. Returns `ZERO` when the
length is zero or not finite. **Never divide without checking** — §4.7 has no
panics, and a `NaN` that escapes here poisons every sum it later touches.

**8.** Add `pub fn from_angle(radians: f32) -> Vec2` — `(cos, sin)`. This is the
one that matters: `Balance::heading` and every `Sign::placement` in the whole
compiler is an angle, and this is how an angle becomes a push.

**9.** Add `pub fn to_angle(self) -> f32` — `y.atan2(x)`.

Remember the M5 bug: `atan2(-0.0, -0.0)` is `-π`, not `0.0`. A zero vector has no
angle. Decide what you return for it and write the reason in the doc comment.

**10.** Implement the operators, from `std::ops`:

```rust
impl std::ops::Add for Vec2 { type Output = Vec2; fn add(self, rhs: Vec2) -> Vec2 { /* … */ } }
```

and the same shape for `Sub`, `Neg`, `Mul<f32>`, `AddAssign`. Five impls, one
line of body each.

`Mul<f32>` lets you write `v * 2.0`. It does **not** give you `2.0 * v` — that
needs `impl Mul<Vec2> for f32`, and it is fine to skip.

**11.** Tests — `src/tests/vec2.rs`, wired with the three-line `#[path]` module
(§5). Skeletons:

```rust
#[test] fn a_zero_vector_normalizes_to_zero_rather_than_nan() { }
#[test] fn an_angle_survives_a_round_trip_through_a_vector() { }
#[test] fn adding_a_vector_and_its_negation_gives_zero() { }
#[test] fn length_and_length_squared_agree() { }
#[test] fn scaling_by_zero_gives_the_zero_vector() { }
```

## Part B — the parcel (steps 12–19)

**12.** Make `crates/magic-core/src/sim/parcel.rs`.

**13.** The substance name:

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct SubstanceId(pub String);
```

A newtype over `String`, exactly like `SigilId` — §3.1 and §4.4. `Demand.substance`
is already `Vec<String>` straight out of `sigils.ron`, so an enum here would break
the day someone adds a substance to the data.

`Ord` because sorting by substance is how a later sum stays order-independent.

**14.** The parcel:

```rust
pub struct Parcel {
    pub substance: SubstanceId,
    pub at: Vec2,
    pub velocity: Vec2,
    pub mass: f32,
    pub temperature: f32,
}
```

**15.** Justify each field in the doc comment, because the next person will want
to add six more:

- `substance` — §3.2's conservation model is unenforceable without knowing *what*
  is being conserved
- `at`, `velocity` — the smallest pair that can be integrated
- `mass` — the quantity `must_find` has to take from somewhere
- `temperature` — §2.6 names temperature, velocity and density as the three
  fields elements interact through

**16.** Write down what is deliberately **absent**, and why: no colour (a shell's
business), no lifetime (M6.6), no owning spell id (M6.4 decides whether parcels
even remember where they came from). An honest hole beats a field nobody reads.

**17.** Add `pub fn new(substance: SubstanceId, at: Vec2, mass: f32) -> Parcel`,
leaving velocity zero and temperature at a named constant — `AMBIENT`, and give
it a unit in its doc comment.

**18.** Add `pub fn momentum(self) -> Vec2` — `velocity * mass`. One line, and
M6.8's conservation test is written against it.

Careful: `Parcel` is not `Copy` (it holds a `String`), so this takes `&self`.

**19.** Tests — `src/tests/parcel.rs`:

```rust
#[test] fn a_new_parcel_is_still_and_at_ambient_temperature() { }
#[test] fn momentum_is_zero_for_a_parcel_that_is_not_moving() { }
#[test] fn two_parcels_of_the_same_substance_compare_equal_by_substance() { }
```

## Part C — the field (steps 20–30)

**20.** Make `crates/magic-core/src/sim/field.rs`.

**21.** One cell:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Default)]
pub struct Cell {
    pub density: f32,
    pub temperature: f32,
    pub flow: Vec2,
}
```

All three are **derived** from the parcels, never authored. That is the invariant
worth stating out loud in the doc comment: a cell is a summary, and if you ever
find yourself writing to one directly, the parcel it should have come from is
missing.

**22.** The field:

```rust
pub struct Field {
    cells: Vec<Cell>,
    parcels: Vec<Parcel>,
    width: usize,
    height: usize,
    cell_size: f32,
    origin: Vec2,
}
```

Every field **private**. Callers go through methods, so `cells.len()` can never
drift from `width * height` — the same reason `Catalog` hides its maps.

**23.** `pub fn new(width: usize, height: usize, cell_size: f32, origin: Vec2) -> Option<Field>`.

`Option`, not a bare `Field`: a zero-width grid or a non-positive `cell_size` is
a caller's mistake, and §4.7 says report it rather than panic on the divide.

**24.** A private `fn index(&self, col: usize, row: usize) -> usize` — the
row-major `row * self.width + col`. Private because a raw index is meaningless
outside this file.

**25.** `pub fn cell_at(&self, at: Vec2) -> Option<(usize, usize)>` — world
position to cell, `None` when it lands outside the grid.

The arithmetic: subtract `origin`, divide by `cell_size`, floor, and check
against `width`/`height`. Do the negative check **before** casting to `usize` —
casting `-1.0` to `usize` in Rust is a saturating `0`, which silently puts
something off the left edge into the first column.

**26.** `pub fn cell(&self, at: Vec2) -> Option<&Cell>`, built on step 25.

**27.** `pub fn add(&mut self, parcel: Parcel)` and
`pub fn parcels(&self) -> &[Parcel]`.

A `Vec` and not a `HashMap` keyed by cell: §4.3 forbids map iteration order in
simulation paths outright, and a `Vec` in insertion order is the cheapest thing
that is deterministic.

**28.** `pub fn settle(&mut self)` — recompute every cell from the parcels.

Clear all cells, then walk `parcels` once: find each parcel's cell, add its mass
to `density`, accumulate `mass * temperature` and `mass * velocity`, then divide
the two accumulators by that cell's density at the end. Mass-weighted, so a
speck cannot outvote a boulder.

**This is where M5.6's bug lives again.** Float addition is not associative, so
the sum depends on the order you add in. Here that is safe *only* because
`parcels` has one fixed order — say so in the comment, because the moment
something sorts or filters that list, the answer changes in the last decimal and
the property test in step 30 is the only thing that will tell you.

Parcels outside the grid contribute to no cell. That is correct, not a bug, and
M6.2 is where you decide whether they should have been clamped instead.

**29.** `pub fn mass(&self) -> f32` — the total across all parcels. Trivial, and
it is the number every conservation test in M6.8 is written against.

**30.** Tests — `src/tests/field.rs`:

```rust
#[test] fn a_field_with_no_width_is_refused_rather_than_panicking() { }
#[test] fn a_position_left_of_the_origin_is_outside_the_grid() { }
#[test] fn a_position_on_the_origin_lands_in_cell_zero_zero() { }
#[test] fn a_position_past_the_far_edge_is_outside_the_grid() { }
#[test] fn settling_puts_a_parcels_mass_in_the_cell_it_sits_in() { }
#[test] fn a_cell_holding_two_parcels_reports_their_combined_mass() { }
#[test] fn a_cells_temperature_is_weighted_by_mass_not_by_count() { }
#[test] fn a_parcel_outside_the_grid_contributes_to_no_cell() { }
#[test] fn settling_twice_gives_the_same_field_as_settling_once() { }
#[test] fn total_mass_is_unchanged_by_settling() { }
```

The last two are the ones that earn their keep: `settle` is called every frame,
so it must be **idempotent**, and it must never invent or lose mass.

## §4.8 — how you will reach it from the panel

A change to core is not finished until the panel can produce its input and show
its answer. For M6.1 that is deliberately deferred to **M6.7**, because there is
nothing to *do* to a field yet — no motion, no spell feeding it. What lands at
M6.7 is a `field` toggle and the overlay drawing the grid, cell density as
shading, and each parcel as a dot.

Record the pairing in §9 when it lands: *what went into core*, and *which button
reaches it*. Until then M6.1 is honestly half-finished, and saying so is better
than a button that toggles nothing.
