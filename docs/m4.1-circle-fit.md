# M4.1 — Fit a circle to a stroke (Taubin)

You draw a loop. The engine has to answer three questions about it:

1. **Where is it?** — centre and radius, so signs can be tested for containment.
2. **How circular is it?** — canon: *"spells will have a fleeting effect or may
   even fail to activate completely if the ring is not circular enough."*
   Circularity is not decoration. It is an **activation gate**.
3. **Is it even a ring?** — or is it a scribble, an oval, a figure-8.

This task answers 1 and 2. Question 3 needs two more signals that arrive in
M4.2–M4.3; the fit is only the first of the three.

---

## What you are building

```
crates/magic-core/src/circle.rs
```

One public function. Takes a slice of `Point`, returns `Option<CircleFit>`.
No Bevy, no `std::fs`, no panics (§4.1, §4.7).

It goes in `magic-core`, not `apps/canvas`, because it is a decision about what
magic *means* — how good a ring is. Shells are thin (§4.2).

---

## 0. Every symbol, spelled out

Skip nothing here. Every later section reuses these names.

### The data — things you are given

| Symbol | Meaning |
| --- | --- |
| `n` | How many points in the stroke. A number, e.g. 213 |
| `i` | Which point you are currently looking at. Runs `0, 1, 2, … n−1` |
| `xᵢ` | The x coordinate of point number `i`. "x sub i" |
| `yᵢ` | The y coordinate of point number `i` |

`xᵢ` is not a new variable per point — it is *one* variable, and `i` selects
which point it currently refers to. In Rust, `points[i].x`.

### The answer — things you are solving for

| Symbol | Meaning |
| --- | --- |
| `a` | x coordinate of the circle's **centre** |
| `b` | y coordinate of the circle's **centre** |
| `r` | the circle's **radius** |

Three unknowns. Every circle in the plane is exactly one `(a, b, r)`.

The equation of that circle:

```
(x − a)² + (y − b)² = r²
```

Read as: a point `(x, y)` is on the circle when its distance from `(a, b)` is
exactly `r`. Nothing more mysterious than Pythagoras.

### The working — things you invent to make the maths easier

| Symbol | Meaning |
| --- | --- |
| `x̄`, `ȳ` | "x bar", "y bar" — the **mean** of all `xᵢ`, of all `yᵢ`. The centroid |
| `uᵢ` | `xᵢ − x̄` — the point's x, measured from the centroid instead of the origin |
| `vᵢ` | `yᵢ − ȳ` — same for y |
| `zᵢ` | `uᵢ² + vᵢ²` — squared distance of point `i` from the centroid |
| `λ` | "lambda" — the **bias-correction root**. The one number that makes this Taubin and not Kåsa. §3 |
| `Cov` | `Muu·Mvv − Muv²` — how much the point cloud is spread in 2D rather than squashed onto a line |
| `DET` | The determinant of the final 2×2 solve. Zero means no unique answer |
| `dᵢ` | `distance from point i to the fitted centre`. Used only *after* the fit, to score it |
| `rms` | Root-mean-square of `dᵢ − r`. Your circularity number, in pixels |

Note `zᵢ` is defined on the **centred** coordinates `uᵢ, vᵢ`, not on the raw
`xᵢ, yᵢ`. Getting that wrong is the single most common way to break this file.

### The moments — nine sums, one pass

A **moment** is just "the average of some product over all points". They are
the entire summary of your stroke that the fit needs. After computing them you
can throw the points away (until scoring).

| Symbol | Definition | Plain words |
| --- | --- | --- |
| `Muu` | mean of `uᵢ · uᵢ` | how wide the cloud is |
| `Mvv` | mean of `vᵢ · vᵢ` | how tall |
| `Muv` | mean of `uᵢ · vᵢ` | how tilted |
| `Muz` | mean of `uᵢ · zᵢ` | how the "far-ness" leans in x |
| `Mvz` | mean of `vᵢ · zᵢ` | how the "far-ness" leans in y |
| `Mzz` | mean of `zᵢ · zᵢ` | spread of the far-ness itself |
| `Mz` | mean of `zᵢ` — also equals `Muu + Mvv` | average squared radius from centroid |

`Mz = Muu + Mvv` is free: `zᵢ = uᵢ² + vᵢ²`, so averaging both sides gives it.
Compute it either way — but assert they match in a test, because if they don't,
your centring is broken.

### The notation

| Symbol | Meaning |
| --- | --- |
| `Σ` | "sigma" — add up over every point. `Σuᵢ` = `u₀ + u₁ + … + u_{n−1}` |
| `mean(…)` | `Σ(…) / n`. Everything above is a mean, not a bare sum |
| `Σx²` vs `(Σx)²` | **Not the same.** `Σx²` = square each, then add. `(Σx)²` = add, then square. For `x = [1, 2]`: `Σx² = 5`, `(Σx)² = 9` |

Means rather than raw sums throughout, because it keeps the numbers small.
A 200-point stroke at screen scale has `Σz²` in the billions; `Mzz` stays
manageable, and `f32` (§4.5) has only ~7 digits to spend.

---

## 1. Why not just solve it directly

The honest thing to minimise is **geometric error**:

```
E_geom = Σ ( dᵢ − r )²        where  dᵢ = √((xᵢ−a)² + (yᵢ−b)²)
```

"Add up how far each point misses the circle, squared." This is the right
answer — it is the maximum-likelihood estimate if your hand-wobble is Gaussian.

It is also **not solvable in closed form**. That square root over `a` and `b`
means you cannot rearrange into linear equations. You would need
Levenberg–Marquardt: guess, improve, repeat, 3–10 passes over the data, with a
chance of diverging on a near-straight stroke.

So the whole algebraic-fit family exists to get *almost* that answer in **one
pass, no guessing, no iteration over data**.

---

## 2. The algebraic family, and Kåsa's flaw

Rewrite the circle equation in **implicit form**:

```
A(x² + y²) + Bx + Cy + D = 0
```

Any circle is some `(A, B, C, D)` with `A ≠ 0`. Recover the real answer with
`a = −B/2A`, `b = −C/2A`, `r² = (B² + C² − 4AD) / 4A²`.

Why bother? Because with `z = x² + y²` treated as if it were just another
coordinate, this is **linear** in `A, B, C, D`. Linear means solvable.

The catch: you cannot minimise nothing — `(0,0,0,0)` fits everything. You need
a constraint that pins the scale. **Every algebraic method is the same
minimisation with a different constraint.**

| Method | Constraint | Arc bias |
| --- | --- | --- |
| Kåsa | `A = 1` | **bad** |
| Pratt | `B² + C² − 4AD = 1` | small |
| **Taubin** | mean gradient magnitude = 1 | very small |
| Hyper | Pratt/Taubin blend | ~zero |

### What Kåsa gets wrong

Kåsa minimises the **algebraic** residual:

```
zᵢ − r²  =  (dᵢ − r)(dᵢ + r)
```

Not `dᵢ − r`. There is a stray `(dᵢ + r)` factor weighting outer points harder.
On a full circle that factor is near-constant and cancels out — harmless. On an
**arc** it does not, and the fit systematically shrinks `r` and drags the centre
into the arc.

| Arc drawn | Kåsa radius error |
| --- | --- |
| 360° | <0.5% |
| 180° | few % |
| 120° | 10%+ |

**Why this matters here specifically.** You must fit arcs:

- Canon rule 2 — a ring with a gap is a legal prepared spell. You still have to
  measure it.
- Canon rule 3 — a split seal is half a ring on each of two objects. That is a
  ~180° arc, and both halves must fit the *same* centre and radius or "touching
  them completes the ring" never fires.

And the deeper reason, from §0 question 2: canon makes circularity an
activation gate. `rms` is measured *against the fitted circle*. If the fitted
centre is wrong, `rms` measures **your hand's error plus the fitter's error**,
mixed, with no way to separate them. A neat 200° arc would score as sloppy and
the spell would fizzle.

**You cannot measure neatness with a bent ruler.** That is the reason for
Taubin. Not speed — see the note at the end of §10.

## 3. The one idea: Taubin is Kåsa plus a correction number

This is the part worth understanding. Everything else is arithmetic.

After centring (§4), Kåsa collapses to a plain 2×2 solve:

```
[ Muu  Muv ] [ 2a ]   [ Muz ]
[ Muv  Mvv ] [ 2b ] = [ Mvz ]
```

Taubin solves the *same shape*, with one number `λ` subtracted from the
diagonal:

```
[ Muu−λ   Muv  ] [ 2a ]   [ Muz ]
[  Muv   Mvv−λ ] [ 2b ] = [ Mvz ]
```

**`λ = 0` gives you Kåsa exactly.** `λ` is the bias correction and nothing else.
It is the smallest root of one cubic polynomial built from the moments.

That is the whole upgrade. Same moments, same solve, one extra scalar found by
Newton's method on four numbers — never on your data. Cost over Kåsa: about
twenty flops, total, regardless of stroke length.

---

## 4. Centring — do this first, always

Replace every `(xᵢ, yᵢ)` with `(uᵢ, vᵢ) = (xᵢ − x̄, yᵢ − ȳ)` before anything
else. Two reasons, both real:

**Conditioning.** At screen coordinates like `(940, 512)`, `z ≈ 1.1 million`
and `z² ≈ 1.2 × 10¹²`. `f32` holds ~7 significant digits. Subtracting numbers
that large loses most of them and the fit turns to noise. Centred, the values
are the size of your stroke.

**Simplicity.** `Σuᵢ = 0` and `Σvᵢ = 0` by construction, so every term with a
bare `u` or `v` in it vanishes. That is what turns a 3×3 into a 2×2, and what
makes the cubic in §6 as short as it is.

At the very end, add `x̄` and `ȳ` back to the centre. **The radius needs no
correction** — shifting everything does not change how big the circle is. If
you find yourself adjusting `r` for the centring, you have a bug.

### And normalise, while you are there

After centring, also divide every `uᵢ, vᵢ` by `s`, the RMS distance from the
centroid:

```
s = √( mean( uᵢ² + vᵢ² ) )
```

This makes `Mz` exactly `1.0` and every other moment order-one. Two payoffs:

- **Epsilons become meaningful.** `Cov` for a real circle is `0.25`; for
  collinear points it is `0 ± 10⁻⁷`. A fixed `1e-6` threshold cleanly separates
  them. On raw screen coordinates `Cov` runs to `10⁷` and its rounding noise
  alone is a few whole units — no absolute epsilon can work there.
- The fit is scale-equivariant anyway, so this changes no answer.

Undo it at the end: multiply the centre offset **and** the radius by `s`.
`Mz == 1.0` also becomes a free assertion that your centring is right.

## 5. The cubic

With the seven moments in hand, build four coefficients:

```
Cov  = Muu·Mvv − Muv²
VarZ = Mzz − Mz²          ← variance of z, NOT its second moment

c3 = 4·Mz
c2 = −3·Mz² − Mzz         ← this one really does want the raw Mzz
c1 = VarZ·Mz + 4·Cov·Mz − Muz² − Mvz²
c0 = Muz·(Muz·Mvv − Mvz·Muv) + Mvz·(Mvz·Muu − Muz·Muv) − VarZ·Cov
```

**`VarZ` in `c1` and `c0`, `Mzz` in `c2`.** Writing `Mzz` in all three compiles,
runs, and fits full circles to the pixel — it only goes wrong on arcs, which is
the one case the whole method exists for. It got written that way here first;
`fit_of_a_half_arc_recovers_the_full_circle` returned 157 for a circle of
radius 100 and nothing else complained.

These define the polynomial whose smallest non-negative root is `λ`:

```
P(λ) = c3·λ³ + c2·λ² + c1·λ + c0
```

Do not expand it that way in code. Use **Horner's form** — fewer
multiplications and better rounding:

```
P(λ)  = c0 + λ·(c1 + λ·(c2 + λ·c3))
P′(λ) = c1 + λ·(2·c2 + 3·c3·λ)
```

`P′` is the derivative — the slope. Newton needs it.

### Newton from zero

```
λ ← 0
repeat at most ~20 times:
    step = P(λ) / P′(λ)
    λ_new = λ − step
    stop if λ_new is not finite
    stop if λ_new == λ            (converged; f32 equality is correct here)
    stop if |P(λ_new)| >= |P(λ)|  (not improving — take the previous λ)
    λ ← λ_new
```

Starting at `λ = 0` is deliberate, not arbitrary: zero is the Kåsa answer, and
the root you want is the one nearest it. Newton walks from Kåsa to Taubin.

The `|P(λ_new)| >= |P(λ)|` guard is what keeps this from ever looping or
wandering. If the correction is not helping, you stop and keep what you had —
and what you had, in the worst case, is Kåsa. **This function has no failure
mode where iteration ruins the answer.** That is why the iteration count is a
safety net and not a tuning knob.

## 6. Centre and radius from `λ`

```
DET = λ² − λ·Mz + Cov

a_c = ( Muz·(Mvv − λ) − Mvz·Muv ) / (2·DET)
b_c = ( Mvz·(Muu − λ) − Muz·Muv ) / (2·DET)

r   = √( a_c² + b_c² + Mz )

centre = ( a_c + x̄ , b_c + ȳ )
```

`a_c, b_c` are the centre **in centred coordinates** — hence adding the
centroid back on the last line.

Two things worth checking you believe:

**Set `λ = 0`.** Then `DET = Cov` and `a_c = (Muz·Mvv − Mvz·Muv) / (2·Cov)`,
which is Cramer's rule on the Kåsa 2×2 from §3. The two methods really are the
same code with one number different.

**The radius formula.** Mean squared distance from points to the centre is
`mean(|pᵢ − c|²)`. Expand: `mean(|pᵢ|²) − 2·c·mean(pᵢ) + |c|²`. Centring made
`mean(pᵢ) = 0`, so the middle term dies and you are left with `Mz + |c|²`.
That is `a_c² + b_c² + Mz`. No summation needed — it was already in the moments.

## 7. Scoring the fit

Separate O(n) pass, *after* you have `(a, b, r)`:

```
dᵢ  = √( (xᵢ − a)² + (yᵢ − b)² )        ← raw coordinates, not centred
rms = √( mean( (dᵢ − r)² ) )
```

`rms` is in pixels: "on average, my ink sits this far off a perfect circle."

Store `rms`, not a normalised score. The caller divides by `r` when it wants a
size-independent number:

```
quality = (1 − rms / r).clamp(0.0, 1.0)     ← for Ring::new
```

**Never report the algebraic residual instead.** It is in units of length², so
it scales with the circle — a large neat ring would score worse than a small
sloppy one. Canon says larger seals are *stronger*, not messier. Normalising by
`r` is what makes "neat" mean the same thing at every size.

**Later, and not now (M4.2):** to stop the pen-hook at stroke start dragging the
fit, you will fit on trimmed points but measure `rms` on **all** points,
including the trimmed ones. Trimming is for finding the circle, never for
scoring the hand — the messiness is the thing canon grades. Leave a comment
saying so when you get there, or you will "tidy" it away later.

## 8. When it must return `None`

No panics in core (§4.7). Every one of these is reachable from real input.

| Situation | Test | Why |
| --- | --- | --- |
| Fewer than 3 points | `points.len() < 3` | Three points minimum define a circle |
| All points identical | `Mz` ≈ 0 | A dot. Every circle through it is equally good |
| Points on a straight line | `Cov` ≈ 0, and `DET` ≈ 0 after solving | A line is a circle of infinite radius |
| Newton produced garbage | `λ` not finite | Guard, should not happen |
| Degenerate solve | `DET` ≈ 0 or not finite | Division by ~zero → ±∞ |
| Impossible answer | `r` not finite, or `r <= 0` | Last line of defence |

`≈ 0` means "below a small epsilon", never `== 0.0`. Floating point almost
never lands exactly on zero.

**Do not test `Cov ≈ 0` alone and bail.** A tight arc can have small `Cov` and
still fit fine. Test `DET` — that is the quantity you actually divide by.

Check `is_finite()` on the way out even if every input was finite. `f32`
division makes infinities silently, and an infinite radius flows into `Ring`
and breaks something three milestones from now with no clue where it came from.

## 9. The shape of the code

```rust
/// A circle fitted to a stroke, and how well it fits.
#[derive(Debug, Clone, Copy, PartialEq)]
pub struct CircleFit {
    /// Centre. `stroke_id` carries the stroke this was fitted to.
    pub center: Point,
    pub radius: f32,
    /// Mean distance of the ink from the fitted circle, in pixels.
    pub rms: f32,
}

/// Fits a circle to `points` by Taubin's method.
///
/// Returns `None` when the points cannot determine a circle — fewer than
/// three of them, or collinear, or coincident.
pub fn fit(points: &[Point]) -> Option<CircleFit>
```

Three private helpers, each testable alone:

```rust
fn moments(points: &[Point]) -> Option<Moments>   // centroid + the seven means
fn taubin_root(m: &Moments) -> Option<f32>        // Newton for λ
fn rms(points: &[Point], center: Point, radius: f32) -> f32
```

`Moments` is a private struct holding `x̄, ȳ, Muu, Mvv, Muv, Muz, Mvz, Mzz, Mz`.
Making it a struct rather than a nine-tuple is worth it the first time you have
to read the code again.

`fit` ignores `stroke_id` entirely for the maths — it fits whatever slice it is
handed. Splitting a pad into strokes is a caller's job, and keeping it out of
here is what lets M4.3 fit two halves of a split ring separately (rule 3).

For `CircleFit.center.stroke_id`, take it from `points[0].stroke_id`. It is not
used in any calculation; it is a breadcrumb for M4.4.

Copy these in as-is during Phase B. Empty bodies compile and pass, which is the

```rust
#[test] fn fit_of_a_perfect_circle_recovers_its_centre_and_radius() { }
#[test] fn fit_is_translation_invariant() { }
#[test] fn fit_is_rotation_invariant() { }
#[test] fn fit_is_scale_equivariant() { }
#[test] fn fit_of_fewer_than_three_points_is_none() { }
#[test] fn fit_of_collinear_points_is_none() { }
#[test] fn fit_of_identical_points_is_none() { }
#[test] fn fit_ignores_stroke_id() { }
#[test] fn fit_of_a_half_arc_recovers_the_full_circle() { }
#[test] fn fit_of_a_quarter_arc_beats_kasa() { }
#[test] fn rms_of_a_perfect_circle_is_zero() { }
#[test] fn rms_grows_with_wobble() { }
#[test] fn mz_equals_muu_plus_mvv() { }
#[test] fn fit_of_a_huge_offset_circle_stays_accurate() { }
```

Notes on the interesting ones:

- **`fit_is_scale_equivariant`** — double every coordinate, the radius doubles
  and `rms` doubles. `rms/r` does not change. That is the property canon rule 8
  depends on.
- **`fit_of_a_half_arc_recovers_the_full_circle`** — generate points on a known
  circle for `θ ∈ [0, π]` only. This is the test that fails on Kåsa and passes
  on Taubin. It is the whole reason for this file's design; write it early.
- **`fit_of_a_quarter_arc_beats_kasa`** — you will not have a Kåsa to compare
  against. Assert against the known truth instead, with a tolerance Kåsa could
  not meet (radius within 1%). Rename to
  `fit_of_a_quarter_arc_is_within_one_percent` if that is clearer to you.
- **`fit_of_a_huge_offset_circle_stays_accurate`** — a circle of radius 200
  centred at `(5000, 5000)`. This is the test that catches missing centring.
  Without §4 it fails badly; with it, it passes exactly. Do not skip it.
- **`rms_grows_with_wobble`** — two strokes, same circle, one with noise added.
  Assert the noisy one has strictly larger `rms`. You are testing monotonicity,
  not a magic number.

Float comparison: never `assert_eq!` on an `f32` result. Write a helper

```rust
fn close(a: f32, b: f32, eps: f32) -> bool
```

and use `assert!(close(fit.radius, 50.0, 0.01))`. A perfect-circle fit will not
give you exactly `50.0`, and it does not need to.

**A note on speed, so you do not worry about it.** A 200-point stroke costs
~1–3 µs here. Your frame budget is 16 700 µs, and $P against 35 templates will
cost ~1 ms of it. Circle fitting is 0.02% of a frame. Taubin costs the same as
Kåsa because the per-point pass is identical. There is nothing to optimise —
write it clearly.

## What shipped

`crates/magic-core/src/circle.rs`, 78 tests green in the crate. Public surface:

```rust
pub struct CircleFit { pub center: Point, pub radius: f32, pub rms: f32 }
impl CircleFit { pub fn quality(&self) -> f32 }   // 0..=1, rms normalised by r
```

Three private helpers behind it: `moments` (centre, normalise, accumulate),
`taubin_root` (Newton for `λ`), `rms` (score, raw coordinates).

the overlay cannot disagree about what neatness means.

Two epsilons, not one: `COINCIDENT_EPSILON` is in pixels and catches a stroke
stacked on one spot; `SOLVE_EPSILON` is dimensionless and only makes sense
because §4 normalised the stroke first.

Measured on the arcs canon forces you to handle:

| Input | True radius | Fitted |
| --- | --- | --- |
| Full circle | 100 | 100.00 |
| Half arc (180°) | 100 | within 1.0 |
| Quarter arc (90°) | 100 | within 1.0 |
| Circle at (5000, 5000) | 200 | within 0.5 |

## Reading the overlay

The debug overlay draws the fit live. Press **F1** to hide it.

**Text**, second block from the top, blue:

```
fit  newest #4 n 213   c 12,-40   r 88.3   rms 2.14px   q 0.976   dev ×5
     fitted 3/5   [#4 r88 q0.98] [#2 r45 q0.91] [#0 r120 q0.55]
```

- `n` — points in the stroke. Under 3 and there is no fit.
- `c` — fitted centre. `r` — fitted radius.
- `rms` — average miss in real pixels. **Not magnified.**
- `q` — `1 − rms/r`, clamped. The number canon rule 8 grades you on.
- `fitted 3/5` — how many strokes on the pad look like circles at all.

**Gizmos**, on the pad:

| What you see | What it is |
| --- | --- |
| Thin blue circle, every stroke | the fitted circle |
| Blue ✕ and dot | the fitted centre |
| **Orange ✕** | the raw **centroid** — mean of the points |
| Two faint blue circles | the ±rms band, magnified ×5 |
| Short red whiskers | each point's miss, magnified ×5, anchored on the circle |

Band and whiskers only draw for the newest stroke. All of them at once is a
smear.

**The orange ✕ is the interesting one.** Draw a full ring and it sits under the
blue centre. Draw half a ring and it slides off toward the arc — that gap is
exactly the bias Kåsa would have baked into the answer, and Taubin does not.
Watching it separate while the blue circle stays put is the whole argument for
this file, on screen.

Whiskers are magnified ×5 (`DEVIATION_GAIN`) because a neat ring misses by two
pixels out of three hundred. The `rms` figure in the text is honest; the
drawing is exaggerated so you can see it. The readout prints `dev ×5` so the
two are never confused.

## If you change it and it breaks

If it compiles but the number is wrong, the suspects in order are:

1. **`zᵢ` computed on raw `xᵢ, yᵢ` instead of centred `uᵢ, vᵢ`** — by far the
   most common. `normalised_moments_have_unit_mean_radius` catches it.
2. **Forgot to add the centroid back** to the centre at the end. Radius right,
   centre wrong by exactly the centroid.
3. **Added the centroid to the radius too.** Radius wrong, centre right.
4. **`Mzz` where `VarZ` belongs, or a sign in `c0`/`c1`.** Circles fit, arcs
   do not. Only `fit_of_a_half_arc_recovers_the_full_circle` catches it.
5. **Sums not divided by `n`.** Everything is wrong by a power of `n`, so it is
   obvious — but only if you look at the actual numbers.

Print `λ` when confused. For a full clean circle it should be very close to
zero; for an arc it should be visibly non-zero. If it is *always* zero you are
computing Kåsa and did not notice.
