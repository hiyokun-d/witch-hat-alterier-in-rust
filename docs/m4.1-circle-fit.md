# M4.1 — Fit a circle to a stroke

Guide for `crates/magic-core/src/circle.rs`. Delete this file when M4 closes.

---

## What you are building

Given a slice of points that roughly lie on a circle, find the circle. Return
its centre and radius, or `None` when the points cannot describe one.

That is the whole task. Deciding whether the fit is *good enough to be a ring*
is M4.2 and M4.4 — not this one. Resist doing them early.

---

## 0. Every symbol, spelled out

Nothing below is guessable from context. Read this once and the rest of the
document stops being Greek.

### The data — things you are given

| Symbol | Is | Where it comes from |
| ------ | -- | ------------------- |
| `xᵢ` | The horizontal position of the *i*-th point | `points[i].x`, world units |
| `yᵢ` | The vertical position of the *i*-th point | `points[i].y` |
| `i` | Which point you are talking about | A loop index, `0..n` |
| `n` | How many points there are | `points.len()` |

The subscript `ᵢ` just means "the *i*-th one". When a formula writes `xᵢ` it is
talking about one specific point; when it writes `x` with no subscript it means
the pattern holds for every point.

### The answer — things you are solving for

| Symbol | Is | Units |
| ------ | -- | ----- |
| `a` | The **x coordinate of the circle's centre** | world units |
| `b` | The **y coordinate of the circle's centre** | world units |
| `r` | The **radius** | world units |

Three unknowns, which is why you need at least three points. Every point you
have gives you one equation; three equations pin down three unknowns exactly,
and more than three means you are averaging out the wobble in a human hand.

`a` and `b` are just a centre point split into two letters. If it helps, read
them as `center.x` and `center.y` — that is literally what they become.

### The working — things you invent to make the maths easier

| Symbol | Defined as | Meaning |
| ------ | ---------- | ------- |
| `zᵢ` | `xᵢ² + yᵢ²` | Squared distance of point *i* from the **origin** |
| `c` | `r² − a² − b²` | A bundle of unknowns, treated as one |

**`z` is a real quantity.** By Pythagoras, `√(x² + y²)` is how far a point is
from `(0, 0)`. Squaring keeps it, and skips the square root you would otherwise
be dragging through the algebra. You compute `z` from data you already have —
it is not an unknown.

**`c` is a bookkeeping trick.** It has no name in geometry you need to care
about, and you never report it. It exists so that a formula containing `r²`,
`a²`, and `b²` — all unknowns, all squared, which is what makes the problem
hard — can be replaced by one unknown that appears once, unsquared.

You solve for `c`, and then §2's last line undoes the substitution to get `r`
back. That is the whole trick: hide the awkward part, solve the easy version,
unhide it.

> If you want the geometric meaning anyway: `c` is minus the *power of the
> origin* with respect to the circle. `c > 0` means the origin is inside your
> circle, `c < 0` means outside. You will never need this, but it is a decent
> sanity check while debugging — draw a ring around the middle of the screen and
> `c` should come out positive.

### The notation

| Symbol | Reads as |
| ------ | -------- |
| `Σ` | "add this up over every point" |
| `Σx` | `points.iter().map(\|p\| p.x).sum()` |
| `Σx²` | Sum of each `x` **squared**: `x₀² + x₁² + …` |
| `Σxy` | Sum of each `x` times *its own* `y`: `x₀·y₀ + x₁·y₁ + …` |
| `Σxz` | Sum of each `x` times *its own* `z` |
| `det` | Determinant — one number describing a matrix, see §4 |
| `ε` | A small number you choose, for "close enough to zero" |

**`Σx²` is not `(Σx)²`.** Square each value, *then* add. Adding first and
squaring after gives a completely different number, and it is the single easiest
way to get a plausible wrong circle out of this. Same for `Σy²`.

**`Σxy` pairs each point with itself.** It is not every `x` times every `y` —
it is `x₀y₀ + x₁y₁ + …`, one term per point.

### The linear algebra

When §3 writes `M·v = k`:

| Symbol | Is |
| ------ | -- |
| `M` | The 3×3 grid of sums — the **coefficients** |
| `v` | The column `[2a, 2b, c]` — the **unknowns** |
| `k` | The column `[Σxz, Σyz, Σz]` — the **known totals** |

`M·v = k` is three ordinary equations stacked. The first row alone says:

```
(Σx²)·2a + (Σxy)·2b + (Σx)·c = Σxz
```

which is one linear equation in three unknowns. Three rows, three unknowns,
solvable.

### Why `2a` and `2b`, not `a` and `b`

Look at where they come from in §2:

```
zᵢ = 2a·xᵢ + 2b·yᵢ + c
```

The `2` is stuck to the unknown. Least squares does not know or care that you
think of `2a` as "twice something" — it just sees three unknown coefficients
multiplying three known quantities, and solves for whatever those coefficients
are.

So what comes back out of the solve is the value of `2a`. **Halve it.** That is
step E5, and forgetting it is the most common way to finish this function with
a centre in the wrong place.

## 1. Why not the obvious approach

The honest thing to minimise is geometric distance: for each point, how far it
sits from the circle's edge.

```
minimise  Σ ( √((xᵢ − a)² + (yᵢ − b)²) − r )²
```

There is no closed-form solution to that. You would need an iterative
optimiser — a loop that guesses, measures, and improves. More code, a
convergence question, and a stopping rule you would have to justify.

There is a trick that makes it linear.

## 2. Kåsa's method

Start from the circle equation and expand it:

```
(x − a)² + (y − b)² = r²

x² − 2ax + a² + y² − 2by + b² = r²

x² + y² = 2ax + 2by + (r² − a² − b²)
```

Look at what is on each side. On the left, `x² + y²` — computable straight from
the data. On the right, `x` and `y` times some unknowns, plus a constant blob.

Give the blob a name:

```
c = r² − a² − b²
z = x² + y²
```

and the equation becomes:

```
zᵢ = 2a·xᵢ + 2b·yᵢ + c
```

**That is linear.** Not in `a`, `b`, `r` — in `2a`, `2b`, `c`. Three unknowns,
one equation per point, and ordinary least squares solves it in closed form.

The radius comes back at the end by undoing the substitution:

```
r = √(c + a² + b²)
```

### What you give up

Kåsa minimises *algebraic* distance, not geometric. In practice it biases the
radius slightly small when the points only cover part of the circle — a short
arc looks flatter than it is, and a flatter arc reads as a bigger... actually,
measure it yourself in the half-arc test rather than taking my word for the
direction. Knowing the size of that bias is what tells M4.2 where its threshold
can safely sit.

For a hand-drawn ring that is nearly closed, the bias is far inside the noise
of the hand that drew it.

## 3. The system to solve

Least squares on `zᵢ = 2a·xᵢ + 2b·yᵢ + c` gives the normal equations. You do
not have to derive these — this is the standard result:

```
⎡ Σx²   Σxy   Σx ⎤ ⎡ 2a ⎤   ⎡ Σxz ⎤
⎢ Σxy   Σy²   Σy ⎥ ⎢ 2b ⎥ = ⎢ Σyz ⎥
⎣ Σx    Σy    n  ⎦ ⎣ c  ⎦   ⎣ Σz  ⎦
```

Every entry is a sum over your points. `n` is the count. Nine sums on the left,
three on the right, one pass through the data.

Note the matrix is symmetric — `Σxy` appears twice, `Σx` twice, `Σy` twice. Six
distinct sums, not nine.

## 4. Solving a 3×3 — Cramer's rule

For `M·v = k`, each unknown is a ratio of determinants:

```
2a = det(M with column 0 replaced by k) / det(M)
2b = det(M with column 1 replaced by k) / det(M)
c  = det(M with column 2 replaced by k) / det(M)
```

So you need one determinant function, called four times.

A 3×3 determinant by cofactor expansion along the top row:

```
        ⎡ m00 m01 m02 ⎤
det M = ⎢ m10 m11 m12 ⎥
        ⎣ m20 m21 m22 ⎦

      = m00·(m11·m22 − m12·m21)
      − m01·(m10·m22 − m12·m20)
      + m02·(m10·m21 − m11·m20)
```

Mind the minus on the middle term. That sign is the single most common bug in
hand-written determinants, and it will not announce itself — you will get a
plausible wrong circle.

**Suggested helper:**

```rust
fn det3(m: [[f32; 3]; 3]) -> f32
```

Taking the matrix as a `[[f32; 3]; 3]` rather than nine arguments makes the
column-replacement step readable: copy the array, overwrite one column, call
`det3` again.

## 5. When it fails

`det(M)` at or near zero means the system has no unique solution. Two ways that
happens, and one check catches both:

- **Fewer than 3 points.** Two points lie on infinitely many circles.
- **Collinear points.** A straight line is a circle of infinite radius, which
  is not representable.

Near-collinear is the interesting case: a very shallow arc gives a tiny but
non-zero determinant, and dividing by it produces an enormous, meaningless
radius. So the test is not `det == 0`, it is `det.abs() < EPSILON`.

Picking that epsilon is a real decision. The determinant scales with the size of
your coordinates — the same shape drawn twice as large gives a much larger
determinant — so an absolute epsilon is scale-dependent. Note that in a comment
even if you take the simple route for now; M4.2 may want to revisit it.

**Core must not panic (§4.7).** Return `None`. No `unwrap`, no division you have
not guarded.

## 6. The shape of the code

```rust
/// A circle fitted to a set of points.
pub struct Fit {
    pub center: Point,
    pub radius: f32,
}

/// Fits a circle through `points`, or `None` when they do not describe one.
pub fn fit(points: &[Point]) -> Option<Fit>
```

`Fit` is plain data — derive what the rest of the crate derives (`Debug`,
`Clone`, `Copy`, `PartialEq`).

`Point` carries a `stroke_id`. **Ignore it.** Fit over whatever points you are
handed, regardless of which stroke each came from.

That is not laziness — canon rule 3 lets one ring be drawn in two halves across
two objects, so this function will eventually be handed points from several
strokes at once. Not caring is the correct behaviour, and building it in now
costs nothing.

`Fit.center` is a `Point`, which needs a `stroke_id` you do not have a
meaningful value for. `0` is fine; say why in a comment.

### Rough shape of the body

1. Bail early if `points.len() < 3`.
2. One pass accumulating the sums. `f32` throughout (§4.5).
3. Build the 3×3 and the right-hand side.
4. `det3` on the base matrix; bail if it is too near zero.
5. Three more determinants, three divisions.
6. Halve the first two results — the solve gives you `2a` and `2b`.
7. Radius from `c + a² + b²`. That is under a square root, so guard it: a
   negative value there means the arithmetic went wrong, and `sqrt` of a
   negative is `NaN` rather than an error you would notice.

Step 7 is easy to skip and produces a `Fit` full of `NaN` that poisons
everything downstream silently. Do not skip it.

## 7. Tests

Colocated in `#[cfg(test)] mod tests`, per §5. Names follow
`<thing>_<condition>_<expectation>`.

```rust
#[test] fn fit_of_a_perfect_circle_recovers_its_centre_and_radius() { }
#[test] fn fit_is_translation_invariant() { }
#[test] fn fit_is_rotation_invariant() { }
#[test] fn fit_of_fewer_than_three_points_is_none() { }
#[test] fn fit_of_collinear_points_is_none() { }
#[test] fn fit_of_identical_points_is_none() { }
#[test] fn fit_ignores_stroke_id() { }
#[test] fn fit_of_a_half_arc_still_finds_the_circle() { }
```

**A generator helps.** Something like "give me `n` points on a circle of radius
`r` centred at `(cx, cy)`, spanning `sweep` radians" covers most of these —
full circle, half arc, and the three-point minimum all come out of one helper.

**Floats will not compare equal.** `f32` trig introduces error in the last
couple of digits, so `assert_eq!` on a recovered radius will fail even when the
maths is right. Compare with a tolerance:

```rust
assert!((got - expected).abs() < 0.01);
```

Pick a tolerance you can defend. If you need `10.0` to pass, something is wrong
and the test is telling you so.

**`fit_is_translation_invariant`** is the sharpest of these. Fit a circle, then
add `(100, 50)` to every point and fit again. The centre must move by exactly
that, the radius must not move at all. It catches an entire family of sign and
indexing errors that the perfect-circle test sails past.

**`fit_of_identical_points_is_none`** — three copies of one point. Length check
passes, determinant is zero. Make sure your guard order actually catches it.
